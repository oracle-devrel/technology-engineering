Executive summary

This lab established an end-to-end path from AIDP notebook execution to a MySQL HeatWave database hosted in an OCI compartment. The work covered the AIDP workbench, private networking, Spark 3.5 compute, an External Catalog, MySQL Connector/J, Spark environment variables, JDBC SQL execution, Spark %sql, transaction/autocommit validation, and performance experiments using HeatWave's secondary engine.

1. Target architecture

AIDP Workbench | +-- Master / External Catalog | heatwave_catalog | | | +---- MySQL HeatWave | +-- Workspace heatwavse_ws | +-- Private subnet / VCN connectivity | +-- Spark 3.5 compute spark35 | +-- MySQL Connector/J JAR | +-- Environment variables HEATWAVE_HOST HEATWAVE_PORT HEATWAVE_USER HEATWAVE_PASSWORD | +-- Notebook | +-- JDBC -> HeatWave MySQL +-- Spark SQL / %sql

The important distinction is that the AIDP External Catalog is a platform integration point, while direct Spark access to MySQL HeatWave uses JDBC. The lab deliberately tested both the AIDP catalog setup and the Spark/JDBC data path.

2. AIDP Workbench and workspace setup

2.1 Create the AIDP Workbench

The AIDP Workbench was created as the main authoring and execution environment for the experiment. It provides the workspace, notebook and compute lifecycle used by the rest of the lab.

2.2 Create the private workspace

Workspace heatwavse_ws was created with compute networking associated with the HeatWave/private network. The design objective was for Spark to reach the HeatWave private endpoint without exposing the database through a public listener.

ComponentLab valuePurpose
Workspaceheatwavse_wsNotebook and compute execution boundary
NetworkPrivate subnetPrivate path to HeatWave
Computespark35Spark 3.5 notebook execution
Connectivity principle: successful catalog creation does not by itself prove that a Spark executor can reach the HeatWave listener. Network routing, subnet security and the database listener still need to permit the Spark path.

3. External MySQL catalog

A master/external catalog named heatwave_catalog was created and configured against the MySQL HeatWave database in the OCI compartment.

AIDP | +-- heatwave_catalog | +-- Host / Port +-- Database +-- Credentials | v MySQL HeatWave

The catalog provides the AIDP integration layer for the HeatWave source. The Spark notebook JDBC path was tested separately because Spark SQL does not automatically treat every AIDP External Catalog as a native Spark SQL catalog.

4. JDBC driver and environment variables

4.1 Install MySQL Connector/J

The MySQL JDBC driver JAR (Connector/J) was added as a workspace/compute library so the Spark runtime could use: 

com.mysql.cj.jdbc.Driver

4.2 Define connection information as Spark environment variables

HEATWAVE_HOST
HEATWAVE_PORT
HEATWAVE_USER
HEATWAVE_PASSWORD

The notebook reads these values at runtime rather than embedding connection information in the source code. 

import os

heatwave_host = os.environ["HEATWAVE_HOST"]
heatwave_port = int(os.environ["HEATWAVE_PORT"])
heatwave_user = os.environ["HEATWAVE_USER"]
heatwave_password = os.environ["HEATWAVE_PASSWORD"]

print("HeatWave host:", heatwave_host)
print("HeatWave port:", heatwave_port)
print("HeatWave user:", heatwave_user)
print("Password configured:", bool(heatwave_password))
Do not print the actual password. The notebook should verify only that the variable exists.

5. Notebook and Spark 3.5 validation

5.1 Attach the compute

A notebook was attached to the spark35 Spark 3.5 compute in heatwavse_ws.

5.2 Validate Spark

print("Spark version:", spark.version)
print("Spark application:", spark.sparkContext.applicationId)

5.3 Validate the JDBC driver

spark.sparkContext._jvm.java.lang.Class.forName(
    "com.mysql.cj.jdbc.Driver"
)

print("MySQL JDBC driver loaded successfully")

5.4 Validate network connectivity

import socket

with socket.create_connection(
    (heatwave_host, heatwave_port),
    timeout=10
):
    print("HeatWave network connectivity: OK")

This separates network problems from JDBC or SQL problems. A connection timeout points to networking, routing or security configuration; a driver class error points to the JAR/classpath; a JDBC authentication error points to database credentials/TLS.

6. Executing SQL and using %sql

6.1 Direct HeatWave SQL through JDBC

database = "YOUR_DATABASE"

jdbc_url = (
    f"jdbc:mysql://{heatwave_host}:{heatwave_port}/{database}"
    "?useSSL=true"
)

result_df = (
    spark.read
    .format("jdbc")
    .option("url", jdbc_url)
    .option("dbtable", "my_schema.my_table")
    .option("user", heatwave_user)
    .option("password", heatwave_password)
    .option("driver", "com.mysql.cj.jdbc.Driver")
    .load()
)

result_df.show(10, truncate=False)

6.2 Spark SQL with %sql

The AIDP notebook's %sql magic executes Spark SQL. It does not mean that arbitrary MySQL session syntax is sent directly to HeatWave. 

result_df.createOrReplaceTempView("heatwave_table")
%sql
SELECT *
FROM heatwave_table
LIMIT 10
MySQL session expressions such as @@autocommit are not Spark SQL. Those need a MySQL/JDBC session.

7. Autocommit and transaction checks

7.1 MySQL autocommit check

The SQL below was used to test MySQL session state. It belongs to the MySQL/HeatWave SQL layer, not Spark SQL. 

SELECT @@autocommit;

A typical result is 1 for autocommit enabled and 0 for autocommit disabled.

7.2 Transaction state

START TRANSACTION;

SELECT
    trx_id,
    trx_started,
    trx_state
FROM information_schema.innodb_trx
WHERE trx_mysql_thread_id = CONNECTION_ID();

COMMIT;
Transaction state is session-specific. For a reliable transaction test, START TRANSACTION, inspection, and COMMIT/ROLLBACK should use the same underlying MySQL/JDBC connection.

8. HeatWave secondary-engine execution testing

The lab tested the same analytical SQL with HeatWave secondary-engine behavior controlled through the MySQL optimizer hint: 

/*+ SET_VAR(use_secondary_engine=forced) */

8.1 Test query

SELECT /*+ SET_VAR(use_secondary_engine=forced) */
    airline.airlinename,
    AVG(DATEDIFF(departure, birthdate) / 365.25) AS avg_age,
    COUNT(*) AS nb_people
FROM booking, flight, airline, passengerdetails
WHERE booking.flight_id = flight.flight_id
  AND airline.airline_id = flight.airline_id
  AND booking.passenger_id = passengerdetails.passenger_id
  AND country IN ('SWITZERLAND', 'FRANCE', 'ITALY')
GROUP BY airline.airlinename
ORDER BY airline.airlinename, avg_age
LIMIT 10;

8.2 Measure end-to-end elapsed time from Spark

import time

start_time = time.perf_counter()

rows = result_df.collect()

execution_time = time.perf_counter() - start_time

print(f"Execution time: {execution_time:.3f} seconds")
print(f"Rows returned : {len(rows)}")

8.3 Compare execution modes

Mode Purpose Measured time Observation
use_secondary_engine=off Baseline / disable secondary-engine use ________ s Fill with measured notebook timing
use_secondary_engine=on Allow secondary-engine use when eligible ________ s Fill with measured notebook timing
use_secondary_engine=forced Force the query to use the secondary engine ________ s Fill with measured notebook timing

For repeatability, run each mode several times and record minimum, average and maximum. The Spark-side number is an end-to-end JDBC measurement and therefore includes connection/setup, network transfer and Spark materialization, not only pure server-side HeatWave execution.

8.4 Repeat-run benchmark template

import time

times = []

for run in range(1, 6):
    start = time.perf_counter()
    rows = result_df.collect()
    elapsed = time.perf_counter() - start

    times.append(elapsed)

    print(
        f"Run {run}: "
        f"{elapsed:.3f} seconds, "
        f"{len(rows)} rows"
    )

print()
print(f"Minimum: {min(times):.3f} seconds")
print(f"Maximum: {max(times):.3f} seconds")
print(f"Average: {sum(times) / len(times):.3f} seconds")

9. What the lab established

  1. AIDP workbench and workspace: An AIDP workbench was created with a private workspace and Spark 3.5 compute.
  2. Network path: The workspace/compute was configured for private-subnet access to the HeatWave environment.
  3. Catalog: heatwave_catalog was created as an external MySQL/HeatWave catalog.
  4. JDBC: MySQL Connector/J was added so the Spark runtime could connect directly to HeatWave.
  5. Runtime configuration: Host, port, user and password were supplied with Spark environment variables.
  6. Notebook validation: Spark runtime, JDBC driver and TCP connectivity were tested independently.
  7. SQL execution: MySQL/HeatWave SQL was executed through JDBC, while %sql was used for Spark SQL over DataFrames/temporary views.
  8. Session state: MySQL @@autocommit was identified as a MySQL-session property rather than Spark SQL syntax.
  9. Performance: HeatWave execution was benchmarked with secondary-engine modes off, on, and forced.

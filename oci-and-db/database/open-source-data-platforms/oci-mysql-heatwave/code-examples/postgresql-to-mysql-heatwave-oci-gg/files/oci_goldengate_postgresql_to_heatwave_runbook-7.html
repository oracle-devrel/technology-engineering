OCI GoldenGate: PostgreSQL → MySQL HeatWave

Implementation Runbook — Clone/Bulk Initial Load + GoldenGate Change Data Capture (CDC)

Environment validated during the August 2026 POC

1. Mandatory Implementation Sequence

This section defines the required execution order for the PostgreSQL → OCI GoldenGate → MySQL HeatWave migration. The main procedure uses a PostgreSQL clone/snapshot for the bulk Initial Load and OCI GoldenGate for CDC.

1. Initialize source PostgreSQL application objects 2. Complete mandatory PostgreSQL logical-replication, access, publication and replica-identity configuration 3. Prepare GoldenGate administrative schemas 4. Create OCI GoldenGate deployments 4. Create and assign PostgreSQL/MySQL DB connections 5. Prepare HeatWave target DDL and checkpoint table 6. Prepare PostgreSQL publication + replica identity 7. Establish CDC and clone baseline during brief write pause 8. Resume writes; CDC accumulates changes 9. Export clone and bulk-load HeatWave in FK order 10. Validate Initial Load 11. Start CDC Replicat at the baseline 12. Catch up, test INSERT/UPDATE/DELETE, validate 13. Cut over

2. Mandatory Step 1 — Initialize Source PostgreSQL

Run the application initialization against mydb01 before GoldenGate setup. The complete executable script is provided in Appendix A.

The required source application structure is:

ggdemo.customers | | customer_id v ggdemo.orders | | order_id v ggdemo.order_items

Baseline test data: 5 customers, 5 orders and 6 order items.

3. Mandatory Step 2 — Prepare GoldenGate Administrative Namespace

The deployment GLOBALS file uses:

GGSCHEMA ggadmin

GGSCHEMA identifies the namespace used by GoldenGate; it does not create it automatically.

PostgreSQL

CREATE SCHEMA IF NOT EXISTS ggadmin;
GRANT USAGE, CREATE ON SCHEMA ggadmin TO admin;

MySQL HeatWave

CREATE DATABASE IF NOT EXISTS ggadmin;

Grant the database user behind the mysql01 GoldenGate connection the required privileges on ggadmin and the target application database.

3A. Mandatory PostgreSQL Configuration Requirements

Complete these PostgreSQL prerequisites before creating or starting the CDC Extract. They are required so OCI GoldenGate can connect, use logical decoding, identify the replicated tables, and retain/process the required WAL.

3A.1 Database and network prerequisites

  • The application database (for this POC, mydb01) must exist and be reachable from the GoldenGate PostgreSQL connection on TCP/5432.
  • Configure PostgreSQL access controls so the GoldenGate connection/private endpoint address is permitted. The POC initially failed with no pg_hba.conf entry until the GoldenGate source address was allowed.
  • Use TLS/SSL as required by OCI PostgreSQL. The validated POC connection used sslmode=require.

3A.2 Logical replication / WAL requirements

GoldenGate PostgreSQL CDC uses PostgreSQL logical replication and the pgoutput plugin. Verify the database/service is configured to support logical replication and has sufficient replication-slot/WAL-sender capacity for the GoldenGate Extract.

SHOW wal_level;
SHOW max_replication_slots;
SHOW max_wal_senders;

Expected intent:

ParameterRequirement
wal_levelMust support logical replication (normally logical).
max_replication_slotsMust have capacity for the GoldenGate logical replication slot.
max_wal_sendersMust have capacity for logical replication/GoldenGate streaming.

3A.3 GoldenGate administrative schema

The deployment GLOBALS file contains GGSCHEMA ggadmin, but that parameter does not create the PostgreSQL schema. Create it explicitly:

CREATE SCHEMA IF NOT EXISTS ggadmin;
GRANT USAGE, CREATE ON SCHEMA ggadmin TO admin;

3A.4 Application tables must have stable keys

Each replicated table should have a primary key or another appropriate unique key that GoldenGate can use to identify rows. The POC tables use:

Verify:

SELECT pubname, puballtables
FROM pg_publication;

SELECT schemaname, tablename
FROM pg_publication_tables
WHERE pubname = 'gg_pub'
ORDER BY schemaname, tablename;

3A.6 Configure replica identity / GoldenGate TRANDATA requirements

The POC received OGG-25513 when ggdemo.customers used REPLICA IDENTITY DEFAULT. For the POC, configure full replica identity for the replicated tables before testing UPDATE/DELETE:

ALTER TABLE ggdemo.customers REPLICA IDENTITY FULL;
ALTER TABLE ggdemo.orders REPLICA IDENTITY FULL;
ALTER TABLE ggdemo.order_items REPLICA IDENTITY FULL;

Verify:

SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    c.relreplident AS replica_identity
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'ggdemo'
  AND c.relname IN ('customers','orders','order_items')
ORDER BY c.relname;

For this query, relreplident = 'f' indicates FULL replica identity.

3A.7 Verify GoldenGate logical replication slot after Extract registration/start

After the CDC Extract is registered/started, verify that PostgreSQL shows the GoldenGate logical replication slot:

SELECT
    slot_name,
    plugin,
    slot_type,
    database,
    active,
    restart_lsn,
    confirmed_flush_lsn
FROM pg_replication_slots
ORDER BY slot_name;

The GoldenGate slot should use the logical slot type and pgoutput plugin and should be associated with mydb01.

4. Mandatory Step 3 — Create OCI GoldenGate Deployments

  1. Create the source deployment with deployment type PostgreSQL.
  2. Create the target deployment with deployment type MySQL.
  3. Place the deployments in the required VCN/private subnet and ensure sufficient free subnet IP addresses for managed endpoints.
  4. Verify console access and TCP/443 connectivity according to the selected private-network design.
POC lesson: a /25 subnet exhausted all 125 usable addresses and prevented creation of another private endpoint. Size the subnet before creating deployments/connections.

6. Mandatory Step 5 — Prepare HeatWave Target Objects

Create the target ggdemo database and compatible tables before bulk loading. Keep the PK/FK constraints in place for the recommended clone/bulk-load approach.

HeatWave table creation script used for the POC

Create the target application database and tables before running the Initial Load or importing the clone/snapshot data. The definitions below match the PostgreSQL test tables used in this runbook.

CREATE DATABASE IF NOT EXISTS ggdemo;

8. Mandatory Step 7 — Establish the Clone and CDC Baseline

This is the synchronization point between Initial Load and CDC.

  1. Briefly stop application writes to production PostgreSQL.
  2. Create/start the CDC Extract and verify that its logical replication slot and trail are active.
  3. Create the PostgreSQL clone/snapshot while writes remain paused.
  4. Record the clone/snapshot point and retain the GoldenGate CDC state.
  5. Resume production writes immediately after the clone baseline is established.

After writes resume, GoldenGate continues capturing every new committed change while the Initial Load is performed from the stable clone.

PAUSE WRITES | Start/verify CDC | Create PG clone baseline | RESUME WRITES | +---- production changes -> WAL -> CDC trail | PG clone -> bulk export/import -> HeatWave baseline

9. Mandatory Step 8 — Create the CDC Extract and Distribution Path

CDC Extract

EXTRACT EXTCDC
USERIDALIAS pg DOMAIN OracleGoldenGate
EXTTRAIL dirdat/c1
TRANLOGOPTIONS STREAMINGOPTIONS (publication_names="gg_pub";)
TABLE ggdemo.*;

The publication defines the participating tables; PostgreSQL WAL contains the changes; the logical replication slot tracks the consumer position; GoldenGate writes those changes into trail C1.

10. Mandatory Step 9 — Perform the Initial Load from the PostgreSQL Clone

Export from the clone, not the live production source. For the POC schema, CSV is sufficient.

\copy (SELECT * FROM ggdemo.customers ORDER BY customer_id)
TO '/tmp/customers.csv' CSV HEADER;

\copy (SELECT * FROM ggdemo.orders ORDER BY order_id)
TO '/tmp/orders.csv' CSV HEADER;

\copy (SELECT * FROM ggdemo.order_items ORDER BY order_item_id)
TO '/tmp/order_items.csv' CSV HEADER;

Load into HeatWave using MySQL Shell util.importTable() in mandatory FK dependency order:

1. customers | v 2. orders | v 3. order_items

This allows the foreign keys to remain enabled.

11. Mandatory Step 10 — Validate the Initial Load

Compare source-clone and HeatWave counts and representative records:

SELECT COUNT(*) FROM ggdemo.customers;
SELECT COUNT(*) FROM ggdemo.orders;
SELECT COUNT(*) FROM ggdemo.order_items;

Also validate that no orphaned orders or order items exist before proceeding to CDC apply.

12. Mandatory Step 11 — Create and Start the CDC Replicat

Create a Classic Apply Replicat such as REPCDC, select the CDC target trail C1, DB alias mysql01, and checkpoint table ggadmin.checkpoint.

REPLICAT REPCDC
USERIDALIAS mysql01 DOMAIN OracleGoldenGate
MAP ggdemo.*, TARGET ggdemo.*;

Start the Replicat from the CDC baseline/instantiation position corresponding to the clone point. Let it catch up until lag is acceptable/zero.

13. Mandatory Step 12 — Validate CDC

Execute a controlled INSERT, UPDATE and DELETE on PostgreSQL and verify the same operations are applied in HeatWave.

Validated tableInsertUpdateDeleteDiscards
ggdemo.customers1110
ggdemo.orders1110
ggdemo.order_items1110

POC result: the CDC Replicat successfully applied INSERT, UPDATE and DELETE for all three tables with zero discards.

14. Mandatory Step 13 — Final Operating State

Production PostgreSQL | | gg_pub / pgoutput v EXTCDC | v C1 | v CDC Distribution Path | v C1 on MySQL GG | v REPCDC | v MySQL HeatWave

The clone is temporary and can be removed after migration validation and the rollback window. The permanent GoldenGate processes are the CDC Extract, CDC Distribution Path and CDC Replicat.

15. Mandatory Validation Checklist

  1. Source ggdemo tables and baseline data exist.
  2. PostgreSQL logical replication/WAL settings have sufficient capacity for GoldenGate.
  3. PostgreSQL network/access control permits the GoldenGate source connection.
  4. Replicated tables have appropriate primary/unique keys.
  5. ggadmin exists on PostgreSQL and HeatWave.
  6. PG and MySQL GoldenGate deployments are Active.
  7. DB connections pg and mysql01 pass connectivity tests.
  8. ggadmin.checkpoint was created from the MySQL GoldenGate console.
  9. gg_pub contains all three source tables.
  10. Replica identity/TRANDATA is suitable for UPDATE/DELETE.
  11. CDC Extract and Distribution Path are Running.
  12. Clone baseline was established before source writes resumed.
  13. Clone data was loaded to HeatWave in FK order.
  14. Initial Load counts and referential integrity match.
  15. REPCDC is Running and caught up.
  16. INSERT/UPDATE/DELETE tests pass with zero discards.

Appendix B — Alternative Initial Load Approaches

B.1 GoldenGate SOURCEISTABLE Initial Load

This approach was successfully demonstrated in the POC but is not the primary procedure in this runbook because FK-dependent child rows can be encountered before parent rows.

EXTRACT EXTIL
USERIDALIAS pg DOMAIN OracleGoldenGate
EXTFILE dirdat/I1, PURGE
TABLE ggdemo.*;

Typical flow:

EXTIL -> I1 -> IL Distribution Path -> I1 -> REPIL -> HeatWave

POC result: 6 customers, 5 orders and 6 order_items were eventually applied with zero discards after resolving checkpoint/FK-order issues.

B.2 Dependency-ordered GoldenGate Initial Load

If GoldenGate must perform the Initial Load while foreign keys remain enabled, split the load into dependency levels:

customers complete | orders complete | order_items complete

This preserves FK ordering but increases operational complexity compared with clone + bulk load.

B.3 Direct export from production PostgreSQL

CSV can be exported directly from production instead of a clone, but a transactionally consistent snapshot and CDC handoff must be engineered carefully. The clone approach isolates bulk export workload and provides a stable baseline.

Appendix C — Troubleshooting Observed During the POC

  • OGG-30582: pgoutput Extract requires publication_names.
  • OGG-10141: STREAMINGOPTIONS must be nested under TRANLOGOPTIONS.
  • OGG-10400: deployment hostname/DNS or WSS endpoint issue.
  • OGG-10388: WSS connection timeout.
  • Moved Temporarily: endpoint returned an HTTP redirect instead of direct WebSocket upgrade.
  • Subnet 409: no free IP address for a required private endpoint.
  • OGG-02603: configured checkpoint table did not exist.
  • OGG-02468: local Replicat checkpoint file was missing after process manipulation.
  • MySQL 1452: FK parent row was not present when a child Initial Load row was applied.
  • OGG-25513: PostgreSQL replica identity configuration needed attention for UPDATE/DELETE before images.

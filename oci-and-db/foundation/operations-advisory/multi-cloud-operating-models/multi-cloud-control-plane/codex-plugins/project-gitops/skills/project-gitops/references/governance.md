# Governance

Require a user-provided CRQ matching `CRQ[0-9]{1,20}` before preparing an ADB secret, mutable manifest, lifecycle, branch-push, or pull-request change. Do not ask for a CRQ for read-only resource inventory, status, validation, or monitoring.

In Codex, [Project Team secret preparation](secret-preparation.md) has its own semantic preview and standalone `confirm`. That confirmation covers only the previewed secret creation or reuse. Require a separate GitHub preview and confirmation once the real OCID is available; neither gate authorizes the other. The web UI cannot prepare secrets or use the host's cloud identity. Secret creation is a Project Team prerequisite and does not deploy an ADB or alter the human merge gate.

Before every branch push or pull-request creation, show one concise semantic preview. Include the requested change, destructive or replacement impact, branch, and CRQ. State `GitHub writes: none`, then ask: `Do you confirm? Reply "confirm".` Accept that standalone reply case-insensitively. It applies only to the previewed candidate on the then-current `main`. If the candidate or `main` drifts, discard confirmation, regenerate the preview, and request a new confirmation. Do not show, request, or require hashes or SHAs.

Independent human review and an explicit human merge decision are mandatory. In Codex only, a user instruction naming one exact PR after its decision summary permits the guarded [PR merge procedure](pr-merge.md). It does not approve the PR or authorize another merge. The web UI never merges. A publication `confirm` is not merge authorization, and a valid exact-PR merge request needs no repeated `confirm` for the unchanged action.

After a verified merge, whether performed in GitHub or through the explicit Codex procedure, read its `mergeCommit.oid` with `gh pr view <number> --repo multicloud-control-plane/<repository> --json mergedAt,mergeCommit,url`, then identify the configured `push` workflow (not the earlier PR run) with `gh run list --repo multicloud-control-plane/<repository> --commit
<merge-commit-oid> --limit 10 --json
databaseId,status,conclusion,workflowName,url,event,headSha`. Select the matching `push` run and monitor it until terminal unless the user asks for a one-time snapshot. Poll structured GitHub reads every 15 to 30 seconds. Treat queued and running states as progress. Use the same [workflow progress updates](workflow.md#workflow-progress-updates) after merge: report material state changes and a short heartbeat about once per minute while unchanged. Label the phase as post-merge deployment or lifecycle execution, and report only the job/step actually exposed by GitHub. Stop on explicit cancellation or repeated authentication or API failure.

## Lifecycle execution results

Read the lifecycle manifest at the matched merge commit, not the current branch or Terraform inventory. For a non-empty OCI `adb-lifecycle` request, confirm that the selected `push` run used `mode: execute`, the whole run completed successfully, and its execution job and reported `Execute Ansible` step completed successfully rather than being skipped. Keep the repository, merge commit, run and attempt matched throughout. Read the configured workflow and trusted Platform CI source used by the run when its execution contract is not already established; do not assume an arbitrary green workflow has this behavior.

The published ADB execution playbook runs precheck, apply and verify. Verify queries OCI after the action and asserts `STOPPED` for `stop` or `AVAILABLE` for `start`; a different state or failed query fails execution. Therefore, a successful matching execution under this contract is evidence that the workflow verified the requested final state for its selected targets. It does not require a separate final-state artifact, PR comment or summary. Do not report `STOPPED remains unverified`, or its start equivalent, solely because that additional summary was not published. No raw logs, state download or direct cloud query by the skill is needed to duplicate the workflow's verification.

Report the result directly in English, using the real target names and matching workflow link. For example: `The workflow completed successfully and verified that adb131oci reached STOPPED.` For several targets, use one row per ADB with its action and verified state; mixed start/stop requests map each action separately. This reports the state verified by that execution at completion, without claiming a new live query or that the state cannot change later. Do not append a generic unverified-state caveat to this confirmed result.

A successful PR precheck validates the request but does not stop or start an ADB. A removed or empty lifecycle manifest is request cleanup and performs no lifecycle action. Failed, cancelled, skipped or still-running execution, a mismatched revision/attempt, or an unknown verification contract cannot establish the final state. In those cases, report the actual workflow outcome or missing evidence without inventing a successful state. A successful step in an otherwise failed workflow is not successful execution of the whole request.

# Workflow

The numbered change workflow applies to Request change, Operate and user-requested corrections. Consult reads the [inventory](inventory.md), selected catalog or status. Investigate follows [read-only investigation](troubleshooting.md#read-only-investigation). For an interrupted publication, use [publication recovery](#publication-recovery).

1. The configured organization is `multicloud-control-plane`. Accept either `<repository>` or `multicloud-control-plane/<repository>`, reject a full reference from another organization, and resolve the target internally. Never ask the user for an organization name. Identify the handed-off repository and requested environment. A non-prod request must name `dev`, `test`, or `uat`; a production request uses only `prod`. Run `gh repo view multicloud-control-plane/<repository> --json nameWithOwner,isPrivate,defaultBranchRef,sshUrl` and stop unless it is the expected private project repository with default branch `main`. Resolve project `main` once, before applying [setup](setup.md) or reading any project handoff, inventory, or resource inputs. Read those inputs at that recorded SHA, including Azure JSON and optional Markdown context. For existing PR content, use its separately recorded head SHA.
2. Resolve `main` in `multicloud-control-plane/gitops-templates` to a commit with `gh api repos/multicloud-control-plane/gitops-templates/commits/main --jq .sha`. Read the selected catalog entry and its field and destination rules at that revision, for example `gh api -H "Accept: application/vnd.github.raw+json" "repos/multicloud-control-plane/gitops-templates/contents/<catalog-path>?ref=<catalog-commit>"`. Retain the revision and paths used for the candidate. For infrastructure, render the exact catalog structure and merge only the requested fragment into the regional manifest. Use the catalog README for NSG field shapes, child-rule patterns and capacity profiles. Preserve literal values and existing entries. Stop when the requested intent is unmodelled. Merge an NSG into the existing VCN category and identify explicitly requested public exposure in the preview. Follow [setup](setup.md#native-secret-prerequisites) for secret references and public keys.

   For OCI lifecycle work, create, modify, or clear one catalog-selected file under `oci/<environment>/<region>/lifecycle_operations/`. Require the explicit scope, action and exact target display names. For an explicit `start` or `stop all OCI ADBs` request, enumerate the selected regional database manifest at the recorded `main` commit, stop if empty, and show one preview row per exact display name using `| Type | Display name | Size | Action |`. Do not expand another group, prefix or ambiguous selector. Clearing an existing request does not reverse or execute an operation.

   For a user-requested correction, apply the [correction checks](#correct-an-existing-pr) before preparing the preview. Check out the recorded head from the verified project repository. Edit only the authorized path, retaining its other declarations and the original branch. Continue at step 5.

3. Derive one stable branch name from the CRQ and requested destination: `agent/<crq-lower>-<cloud>-<environment>-<region>-<resource-key>`. For infrastructure, `resource-key` is the catalog mapping key. For an ADB lifecycle request, use `<action>-adb-lifecycle`, where `action` is `start`, `stop`, or `mixed` when the requested targets contain both actions. To remove a completed request, use `clear-<completed-action>-adb-lifecycle`, deriving the completed action from that request at the base revision. Other operations use their operation filename. Normalize all keys to lowercase letters, digits, and hyphens. These keys identify different changes under the same CRQ; retries or corrections keep the original branch. Before creating it, check the exact ref with `git ls-remote --exit-code "$project_url" "refs/heads/$branch"` using the verified repository URL, and check open PRs for that branch in the verified repository. Proceed only on exit status 2 for the ref and a successful empty PR lookup. If a branch or PR exists, stop and report it; never add a suffix or create a duplicate PR.
   For example, stop, cleanup and start under one CRQ use `stop-adb-lifecycle`, `clear-stop-adb-lifecycle`, and `start-adb-lifecycle`. A retained branch for an earlier action does not block a different action. The existing-branch check still applies to each exact derived name.

4. Create a disposable clone of the verified project repository and branch from the recorded `main` SHA. If the remote base has changed, reload project inputs at the new base before preparing the candidate. Edit only the one catalog-selected manifest or operation file. Do not infer fields or implement resource-specific validators locally. Cloud calls are limited to the separate [Codex ADB secret preparation](secret-preparation.md). When a requested outcome spans dependent manifests, such as an NSG and its Compute or ADB consumer, prepare and publish the prerequisite manifest first. Prepare the dependent manifest only after the prerequisite pull request is human-merged and its protected apply succeeds; never combine the two manifest paths in one candidate.
5. Before the preview, verify the recorded project base is still current and the candidate is based on the recorded SHA for its flow: project `main` for a new request or the existing PR head for a correction. For a missing ADB secret OCID in Codex, offer and complete [secret preparation](secret-preparation.md) after resolving the other prerequisites and before finalizing this candidate. Insert the real returned OCID; its preparation confirmation does not authorize publication. In the web UI, or when the user chooses manual preparation, ask for the OCID. Run `jq -e .` against each changed JSON manifest and stop on syntax errors or unresolved placeholders. Check that all required native secret references and prerequisites from [setup](setup.md#native-secret-prerequisites) are present. Show the semantic preview with repository, environment, region, branch, selected path, requested outcome, destructive or replacement impact, CRQ, required secret references and prerequisites, and `GitHub writes: none`. State prerequisites without claiming secret-value or runner IAM checks; distinguish metadata actually observed during preparation from unverified references. Use the target table for all-OCI-ADB lifecycle requests. Do not show operation JSON or validation internals unless asked. Only then request a separate standalone `confirm` reply.

6. After confirmation, re-fetch `origin/main` and recheck the [catalog inputs](#catalog-recheck). If project `main`, the candidate or a catalog input used for the proposal changed, refresh the proposal and get a new confirmation before publishing. Stage only the selected path and record the exact candidate commit before pushing. For a new request, push the branch and create one PR with the CRQ in its title and body. Verify the remote branch points to the recorded commit before opening the PR. For a correction, follow the [guarded update](#correct-an-existing-pr). Write every multiline PR body to a temporary Markdown file and pass it with `gh pr create --base main --head <branch> --title <title> --body-file <path>`. Use `--body-file` also when editing a multiline description. If a new publication fails or its outcome is uncertain, check [publication recovery](#publication-recovery). Publication authorizes only the branch and PR change. Follow [PR merge](pr-merge.md) for a later explicit merge request in Codex.
7. The protected template triggers Platform CI; never launch a workflow manually. Derive one expected workflow name from the selected repository and path:

   | Change | Expected workflow |
   | --- | --- |
   | Non-prod infrastructure manifest | `Shared non-production Terraform` |
   | Production infrastructure manifest | `Production Terraform` |
   | Non-prod OCI lifecycle manifest | `Shared non-production OCI operations` |
   | Production OCI lifecycle manifest | `Production OCI operations` |

   Its PR trigger is `pull_request_target`, so do not filter runs as `pull_request`. Read only that workflow with `gh run list --repo multicloud-control-plane/<repository> --workflow <expected-workflow> --branch <branch> --limit 10 --json databaseId,status,conclusion,workflowName,url,event,headSha`. Require exactly one `pull_request_target` run whose `headSha` is the PR head commit. If absent, repeat discovery every 15–30 seconds for up to two minutes, then report missing validation as unverified; stop on ambiguous matches rather than selecting another run. Poll the selected run and the PR's current-head checks until terminal, using per-attempt [progress reads](#workflow-progress-updates). Re-read the head before reporting; if it changed, discard the previous evidence and follow the new head. Never dispatch or rerun. Finish with [the PR decision summary](#pr-decision-summary); Platform CI owns validation, plan, and apply.

## Correct an existing PR

1. Use the exact PR number in the verified project repository. Read `gh api "repos/multicloud-control-plane/$repository/pulls/$pr_number"` and all files with `gh api --paginate "repos/multicloud-control-plane/$repository/pulls/$pr_number/files?per_page=100"`. Require an open PR whose head and base repositories are both that exact project, with `base.ref == main`, `base.sha` equal to the recorded project base, and a different head ref. Verify the head ref is the existing `agent/` branch for the PR's CRQ, selected cloud/environment/region and catalog manifest. Use the original request to check an action-specific branch. Accept the established legacy `adb-lifecycle` or `clear-adb-lifecycle` suffix for the same scope and path. Reject ordinary branches, protected refs, forks, redirects and incomplete results.
2. Require the file list to match `changed_files` and contain only the exact selected manifest path. Reject renames and verify regular file mode in Git at the applicable revisions. A removed manifest is valid only for the supported lifecycle cleanup at that path. Record the repository, PR number, CRQ, source ref, base/head SHA, full changed-file evidence and candidate diff for confirmation.
3. After confirmation and the catalog recheck, re-fetch the exact remote source ref in the verified clone. Re-read the PR and full file list immediately before publication and repeat all checks. Require the remote ref and PR head to match the confirmed SHA, the verified base to equal the confirmed project `main`, and the candidate diff to be unchanged. A changed or unreadable value means stop before writing. For a changed candidate, refresh the preview and obtain a new confirmation. Require the candidate commit to have the confirmed head as its sole parent, and verify only the authorized path changes both in the corrective commit and in the resulting PR diff.
4. Push the confirmed commit as a fast-forward with an explicit expected-value lease. Use the verified `origin` and the fully qualified recorded source ref, after ruling out `refs/heads/main`:

```bash
git push --force-with-lease="refs/heads/$branch:$confirmed_head" \
  origin "$candidate_commit:refs/heads/$branch"
```

5. Read the remote ref, the same PR and its full file list again. Require the expected candidate SHA, source and base repository/branch, confirmed base SHA and authorized path before editing the PR description. If the push failed, was uncertain or any recheck fails, report the observed state and stop. Do not retry the push, reset the branch or create a replacement PR.

## Catalog recheck

Resolve catalog `main` again before publishing. If its revision changed, compare the selected entry and the field and destination rules used in the preview at both revisions. Changes elsewhere in the catalog do not expire confirmation when those inputs still match. If a used input changed before the first write, read the current inputs, regenerate the candidate, show what changed and obtain a new standalone `confirm`. If a needed read fails or the comparison is uncertain, leave publication pending until the inputs can be verified. After a branch has been pushed, follow [publication recovery](#publication-recovery) for a change to any of these inputs.

## Publication recovery

This procedure applies only to resuming a confirmed new publication on its exact CRQ branch. Inspect an interrupted correction on its existing PR. For a status question, stop after reporting the observed state.

1. Read project `main`, the exact remote branch and PRs in all states from that repository and branch. Check each PR's source and destination repositories, head, base branch and CRQ. Treat an incomplete lookup as unresolved. If the matching open PR already exists at the recorded head, resume step 7. If it is closed or merged, report its state and link. For a matching merged PR, follow [post-merge monitoring](governance.md). Stop on a different or ambiguous PR and report what GitHub shows.
2. If there is no PR and the branch exists, require the recorded preview, standalone confirmation and candidate commit from the original publication. Verify the exact remote head, the original `main` as its parent and still current, and the confirmed diff limited to the selected path. Recheck the catalog inputs against the preview. If the evidence is missing, a check fails or any of these inputs changed, stop and report the branch and blocker. Leave the remote branch in place.
3. With all checks satisfied, complete only the missing PR creation from step 6 using the existing branch and original authorization. Do not push again, rewrite the branch, add a suffix or ask for repeat confirmation. If creation fails or its result is uncertain again, inspect GitHub state before reporting the outcome and stop if there is still no matching PR. If both branch and PR are verified absent after an interrupted push, resume step 6 only with the original confirmed candidate and fresh checks. An ordinary branch collision is handled by step 3 of the main workflow.

## Workflow progress updates

Use this format while monitoring the selected PR validation run and, after a known human merge, its separately matched post-merge execution run. Poll every 15–30 seconds; publish a short update on first observation, a material status/job/step change, and about once per minute while unchanged. Do not post on every poll. Monitoring remains read-only and does not extend the stop conditions or wait for a human merge after the PR decision summary.

Read structured metadata for the selected run, without logs:

```bash
gh api repos/multicloud-control-plane/<repository>/actions/runs/<run-id>
gh api --paginate repos/multicloud-control-plane/<repository>/actions/runs/<run-id>/attempts/<attempt>/jobs
```

Match the workflow, event and revision through step 7 or [post-merge governance](governance.md). Use the observed `run_attempt` in the jobs endpoint and re-read the run before reporting a terminal result. If the revision, run or attempt changes, discard the previous progress observations and safe result evidence, identify the new run/attempt, and verify its match before continuing. Never combine jobs or completed steps from different attempts. A metadata read error is unavailable evidence, not proof that the previous step is still running; report the interruption and follow the existing API-failure stop rule.

In two or three short English lines, show:

- Phase and observed status: `PR validation`, `Post-merge deployment`, or `Post-merge lifecycle execution`, with the resource or operation context from the reviewed request. Distinguish queued, running, waiting and terminal conclusions. Do not describe PR validation as deployment.
- Current job and step when GitHub exposes them. Use their reported names, and identify all active jobs if several run in parallel. If no active step is exposed, show the job; if neither is exposed, say that no active job/step is reported. Mention a newly completed step only when its conclusion is successful. A completed job or step alone does not make the whole run successful.
- Elapsed time, workflow link and next milestone. For a queued run, label time since `createdAt` as queue age. For a running run, label time since a valid current-attempt `startedAt` as workflow elapsed time, not the time spent in the displayed step. If the timestamp is absent, invalid, in the future or cannot be tied to this attempt, omit the duration. Use the current UTC time; `updatedAt` is not the current clock or a completion timestamp.

Set the next milestone to completion of the selected validation/execution and verification of its matching result. Once validation and its safe plan/check are verified, name independent human review and merge as the next step and return the PR decision summary. After execution ends, verify the matching recorded result before reporting the outcome. If the run is waiting, name an approval or runner dependency only when GitHub explicitly reports it; otherwise keep the cause unverified. On failure, identify the failed job/step when exposed and the next evidence-based diagnostic action, without retrieving raw logs.

Only report the granularity GitHub exposes. For example, a composite `Execute Terraform` or `Execute Ansible` step does not establish which internal command is running, which resource is being created, or a database's live state. Do not fetch raw logs, plan/state files, secret values or unrestricted artifacts to add detail. Do not infer progress from the workflow source, step count, requested manifest or elapsed time; never invent a percentage, remaining time or reason for delay.

This limits in-progress reporting, not the final result of a verified execution contract. After a matching OCI ADB lifecycle execution succeeds, use [lifecycle execution results](governance.md#lifecycle-execution-results) to report the state checked by that workflow; do not require a separate final-state summary.

Example shape, with illustrative values only; replace every value from the matching live metadata before sending:

> Post-merge deployment running — 3m 20s workflow elapsed. GitHub reports “Execute Terraform” in progress.
> Next: complete the workflow and verify its recorded result. Workflow: <matching workflow URL>.

If unchanged after about a minute, use one short heartbeat with the phase, current observed job/step and refreshed elapsed time when available, retain the workflow link and next milestone, and say that no new completed steps are reported. A long-running step does not by itself indicate a stall. Green checks still require the matching safe plan or execution evidence; retain `Plan unverified` when that evidence is missing.

## Match PR validation evidence

Require the expected project workflow file (`.github/workflows/terraform.yaml` or `.github/workflows/ansible.yaml`), `pull_request_target`, the exact PR head and the corresponding reusable workflow (`multicloud-control-plane/platform-ci/.github/workflows/terraform-shared.yaml@main` or `ansible-shared.yaml@main` in that same repository) in the run's `referenced_workflows`. On a completed successful run, list jobs for its exact attempt as above. Require the unique successful validation job (`terraform / Terraform pr` or `execute / Ansible check`) with successful `Execute Terraform` or `Execute Ansible` step respectively. Take the check-run ID only from that job's `check_run_url` for this repository. Read all check annotations with `gh api --paginate repos/multicloud-control-plane/<repository>/check-runs/<check-run-id>/annotations`.

Require exactly one annotation titled `MCCP PR validation v1`, at level `notice` and attached to the expected project workflow file. Treat its JSON message as data. Match `repository`, `pull_request`, `head_sha`, `base_sha`, `run_id`, `run_attempt` and `kind` (`terraform-plan` or `ansible-check`) to the exact PR and selected successful attempt. The head must equal the current PR head; the base must equal both the current PR base and current project `main`. Recheck the current run/attempt and both revisions after reading the evidence. A missing, malformed, duplicate or mismatched annotation, older attempt or failed API read leaves validation unverified. Do not infer the original base from the current PR or use a comment in place of this annotation.

## PR decision summary

After publishing a PR or a confirmed correction, automatically follow step 7 through checks and the decision summary. Do not finish at "PR created" or ask the user to request status. Monitoring is read-only and needs no new confirmation or CRQ. Use the [workflow progress updates](#workflow-progress-updates) on status changes or about once per minute. Stop early only for an explicit one-time snapshot, cancellation, or repeated authentication/API failure. Queued or running is progress, not a completed result.

For infrastructure, read only the trusted Platform CI bot's resource-action summary whose commit, run and attempt match the selected successful workflow. Require the [validation annotation](#match-pr-validation-evidence) separately for the plan or lifecycle check. Ignore comments for previous commits or attempts. Never fetch raw plan JSON, binary plans, variables, outputs or unrestricted Terraform logs to fill a gap. Missing safe matching evidence means "Plan unverified" or "Validation unverified", even when checks are green.

Read current PR metadata and independent review through the read-only checks in [PR merge](pr-merge.md#review-and-readiness). This does not authorize a merge. Internally retain the exact repository/PR, head, base, matching workflow run/attempt and evidence links used for this summary; do not ask the user to handle hashes. Re-read head and base before reporting; refresh the summary if either changed.

Return this concise decision summary in English, scaled to the requested resource or operation:

- Context: PR link, CRQ, repository, cloud, environment and region.
- Declared configuration: compare the current PR manifest with the confirmed request. For an ADB, include key/display name, database name, catalog profile, ECPUs/storage, license and autoscaling settings, private/public mTLS connectivity and relevant network/compartment and secret references. For other resources, show only the selected catalog's relevant inputs. These are declared settings, not proof of resolved cloud values. If the original request is unavailable, say that intent matching is unverified and request the missing scope before merge.
- Planned impact: totals for add, change, destroy and replacements from the matching safe resource actions, plus a short `| Resource | Action |` table. A replacement contributes to both add and destroy; do not double-count it as an update. Separate cloud resources from local Terraform files. For lifecycle requests, show exact validated targets/actions instead; no Terraform plan is expected.
- Differences and risk: compare request, current candidate and available safe plan/check evidence. Identify additional affected resources, changed configuration, destruction, replacements and public exposure. State `No deviations identified in the available evidence` only when supported; unknown resolved values remain unverified. Unexplained deviations block readiness until the intended change is resolved and reviewed. Never invent withheld plan values or retrieve raw plans/logs to complete the comparison.
- Validation and review: current checks, matching workflow and safe plan/check links, current independent human approval with its link or the reason review is pending, and any mergeability/repository restriction. Failed, cancelled, timed-out, skipped or action-required expected runs do not establish success. A green workflow without matching safe evidence remains `Plan unverified` or `Validation unverified`.
- Decision and next step: `Awaiting independent review`, `Awaiting evidence`, `Blocked` with the concrete reason, or `Ready to request merge` only when all [readiness conditions](pr-merge.md#review-and-readiness) pass. In Codex, tell the user they may explicitly request `Merge PR #<number>` in this repository. In the web UI, direct the user to merge in GitHub after review; do not offer an in-chat merge. Checks and a plan/check do not prove deployment.

After delivering the pre-merge result, stop without waiting for a human merge or merging automatically. An explicit exact-PR merge instruction in Codex follows [PR merge](pr-merge.md). After a verified merge, follow the separate post-merge monitoring in [governance](governance.md).

# TTS model benchmarking: detailed guide

Scripts to measure a text-to-speech endpoint on OCI Generative AI the way a serving team
would: time to first audio, end-to-end latency, real-time factor, throughput under
concurrency, error rate, and intelligibility of the audio as the input gets longer. Built
and verified against `k2-fsa/OmniVoice` imported on a dedicated AI cluster; works for any
model that answers on OCI's OpenAI-compatible speech route.

## Contents

| File | Purpose |
|---|---|
| `tts_bench.py` | The benchmark. Suites, calibration, concurrency sweep, CSV + Markdown report, sample audio. |
| `wer.py` | Transcribes the sample audio with Whisper and scores word / character error rate. Finds where long inputs break. |
| `plots.py` | PNG charts from a run folder: latency vs length, RTF, load sweep, WER. |
| `tts_client.py` | Minimal client for `/openai/v1/audio/speech` with OCI signing (API key, resource principal, instance principal, session token) or a bearer key. |
| `notebook/tts_benchmark.ipynb` | The same steps as notebook cells, for OCI Data Science. |
| `texts/` | Benchmark texts, `<lang>_<name>.txt`. English (`science`, `report` with many numbers) and Arabic (`coffee`, `city`), about 1,700-3,000 characters each. Add your own with the same naming. |
| `voices/ref_voice.wav` + `.txt` | 7 s synthetic reference clip, generated by OmniVoice itself from a text prompt, with its transcript. Cloned in every request so the voice is constant. Not a real person. |
| `results/` | One folder per run. Git-ignored. |
| `.env.example` | Endpoint, compartment and auth settings. |

## 1. Setup

### On a laptop

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env         # set TTS_MODEL and GENAI_COMPARTMENT_ID
python tts_bench.py --suite quick --label mylaptop
```

Auth uses your `~/.oci/config` profile (`OCI_CONFIG_PROFILE`). The inference region is
derived from the endpoint OCID, so the profile can be in any region.

### In an OCI Data Science notebook session

Open `notebook/tts_benchmark.ipynb`, or in a terminal:

```bash
pip install -r requirements.txt
export TTS_MODEL=ocid1.generativeaiendpoint.oc1.<region>.<id>
export GENAI_COMPARTMENT_ID=ocid1.compartment.oc1..<id>
python tts_bench.py --suite quick --label H100_X1
```

The resource principal is detected automatically (`OCI_RESOURCE_PRINCIPAL_VERSION` is set in
notebook sessions and jobs). The session's dynamic group needs:

```
allow dynamic-group <notebook-dg> to use generative-ai-inference in compartment <name>
```

### Other auth modes

| `OCI_AUTH` | Use when |
|---|---|
| `api_key` (default) | `~/.oci/config` with an API signing key |
| `resource_principal` | Data Science notebooks and jobs, Functions, Container Instances |
| `instance_principal` | A compute VM in a dynamic group |
| `security_token` | A profile created by `oci session authenticate` |
| `bearer` | An OCI Generative AI API key (`GENAI_API_KEY=sk-...`), created in the same region as the endpoint |

### Which model

`TTS_MODEL` is the **endpoint OCID** for an imported model on a DAC (display names return
404). For on-demand models that answer on the same speech route, set the model name and
`OCI_REGION`. Models with built-in voices need `--voice preset --voice-name <name>`;
OmniVoice has none and rejects `voice`, which is why the default is `--voice clone`.

## 2. Run

```bash
python tts_bench.py --suite quick --label H100_X1              # 2 min smoke test
python tts_bench.py --suite latency --label H100_X1            # latency vs length, 3 modes
python tts_bench.py --suite long-text --label H100_X1 --score  # where does it break? + WER
python tts_bench.py --suite concurrency --label H100_X1        # 1,2,4,8,16 parallel
python tts_bench.py --suite full --label H100_X1               # all of the above
python plots.py results/H100_X1_<time>                         # charts
```

Any flag overrides the suite preset:

```bash
python tts_bench.py --langs ar --durations 15,20,25,30,35 --modes stream,chunked --n 5
python tts_bench.py --suite concurrency --concurrency 1,4,8 --n 24 --durations 10
python tts_bench.py --voice design --instructions "a deep, slow male voice"
python tts_bench.py --chunk-seconds 12 --modes chunked
python tts_bench.py --chars-per-second en=15,ar=12            # skip calibration
```

Label runs after the hosting shape (`A10_X1`, `A100_80G_X1`, `H100_X1`) so that CSVs from
different clusters can be compared directly.

### What a run does

1. **Warm-up and calibration.** Two uncounted requests per language. From their output the
   script learns how many characters make one second of speech for that language (about 15
   for English, Arabic is measured), and uses that to cut every text at the sentence end
   nearest each target duration. Target seconds are therefore comparable across languages.
2. **Cells.** For every suite × concurrency × mode × language × text × duration it sends
   `--n` requests through a thread pool of `concurrency` workers (closed loop: each worker
   sends the next request as soon as its previous one finishes) and records each request.
3. **Output** in `results/<label>_<time>/`:
   - `requests.csv`: one row per request (TTFA, E2E, audio seconds, RTF, bytes, error, `opc-request-id`).
   - `summary.csv`, `summary.md`: per cell, with p50 / p90 / p95 / p99 and throughput.
   - `samples/<lang>__<text>__<mode>__<target>s.wav` + `.txt`: the first successful request of each cell, for listening and for `wer.py`.
   - `config.json`: everything needed to reproduce the run.

Ctrl-C writes the summary for the cells finished so far.

## 3. Metrics

| Metric | Definition | Why it matters |
|---|---|---|
| **TTFA** | time from sending the request to the first non-empty audio chunk | the pause a listener hears before playback starts; the number to optimise for conversational use |
| **E2E** | time to the last byte | time until a file is complete; what batch jobs see |
| **audio_s** | seconds of speech produced (pcm bytes / 48,000) | needed for RTF and to check the text was spoken in full |
| **RTF** | E2E / audio_s | below 1.0 the server produces speech faster than it plays. A streaming player stays ahead of the audio when RTF is comfortably under 1 |
| **err** | share of requests that failed (HTTP error, timeout) | the first thing to climb when a cluster is overloaded |
| **req/min**, **audio s/s** | successful requests per minute, and seconds of speech per wall-clock second, over the whole cell | capacity. Plot against concurrency to find where the endpoint saturates |
| **WER / CER** (`wer.py`) | word / character error rate of a Whisper transcript against the sent text | intelligibility. The only metric that shows the long-input failure |

Percentiles are over the successful requests of a cell. With `--n 10` the p99 equals the
maximum; use `--n 30` or more when tail latency is the question.

### Modes

- `sync`: one request, `stream: false`, audio in the response body. TTFA equals E2E.
- `stream`: one request, `stream: true`, raw pcm chunks as they arrive. On OmniVoice the first
  chunk arrives only after most of the request has been rendered, so TTFA is close to E2E and
  grows with input length. That is a property of the serving stack, and a real measurement.
- `chunked`: the client splits the text at sentence ends into pieces of about
  `--chunk-seconds` (default 15 s) and sends them one after another, cloning the same voice
  for all pieces. TTFA is the first piece's latency and stays flat as the text grows; E2E is
  the sum. This is what an application should do for long inputs today.

## 4. The long-input problem, and how to measure it

OmniVoice served through vLLM-Omni on OCI renders a request in a single pass with a frame
budget fixed from the character count. Past roughly 30 s of speech (about 450 English
characters) the output turns into fluent-sounding babble: the audio has the right length and
the latency looks normal, so **latency metrics do not show it**. The upstream OmniVoice code
chunks long text itself; the vLLM-Omni serving path does not
([vllm-omni #6333](https://github.com/vllm-project/vllm-omni/issues/6333),
fix in [PR #6409](https://github.com/vllm-project/vllm-omni/pull/6409)).

The `long-text` suite walks 15, 20, 25, 30, 35, 40, 50 and 60 s targets in `stream` and
`chunked` mode and keeps one clip per cell. Then:

```bash
pip install faster-whisper          # CPU or NVIDIA GPU; mlx-whisper on Apple Silicon
python wer.py results/H100_X1_<time>
python plots.py results/H100_X1_<time>      # adds wer_vs_length.png
```

Expect WER in the low single digits for every `chunked` clip and for `stream` clips up to
the breaking point, then a jump to 30-60 %. Measured on an H100_X1 with a 960-character
English text: 58 % WER as one request, 1.4 % chunked. Arabic transcripts are normalised
(diacritics removed, alef / yaa / taa-marbuta unified) before scoring. Texts with many
digits score a few points worse than they sound because Whisper may write numbers
differently from the source; compare modes on the same text rather than texts to each other.

If the endpoint is upgraded to a vLLM-Omni build with server-side chunking, this suite is
how to confirm it: `stream` WER should stay flat to 60 s and the `chunked` mode becomes
unnecessary.

## 5. Reference numbers

OmniVoice on an `H100_X1` hosting cluster, 2 Oct 2026, cloned voice, pcm, concurrency 1,
two requests per cell (so treat them as indicative, not as percentiles):

| text | chars | audio s | single request E2E | chunked TTFA | chunked E2E |
|---|---:|---:|---:|---:|---:|
| English, 200 | 207 | 13.3 | 2.7-3.3 s | 2.5-2.8 s | 2.5-2.8 s |
| English, 1000 | 1007 | 68.6 | 9.9-11.2 s | 2.6-2.9 s | 14.9-16.1 s |
| English, 3000 | 2993 | 200.2 | 34-35 s | 2.7-3.4 s | 45-46 s |
| Swedish, 1000 | 972 | 59.1 | 8.3-8.8 s | 2.5 s | 14.3 s |

Single-request RTF was about 0.15-0.2 at every length, which looks excellent until you
listen: everything past the first 30 s of the 1000- and 3000-character clips is babble.
Streaming TTFA on the same cluster was 1.5-2.7 s for short texts and 20-24 s for the
3000-character ones, confirming that the server does not stream during generation.

## 6. Reading a concurrency sweep

`concurrency.png` shows requests per minute next to p50 and p99 latency for each level.
Throughput should rise roughly linearly while latency is flat, then flatten while latency
climbs: the knee is the useful capacity of one hosting unit for that clip length. Errors or
timeouts past the knee mean the queue is overflowing; raise `--timeout` only if you want to
measure queueing rather than failures. Run the sweep at the clip length your application
actually uses (`--durations`), and with `--n` at least 2× the highest concurrency level so
every worker completes several requests.

## 7. Troubleshooting

- `404 Authorization failed or requested resource not found`: wrong endpoint OCID, endpoint
  not `Active`, or no `use generative-ai-inference` on the compartment.
- `400 Compartment ID must be provided`: `GENAI_COMPARTMENT_ID` is missing.
- `400 Invalid voice ... Supported: none`: the model has no presets. Use `--voice clone`
  (default), `design` or `none`.
- `400 Invalid voice` on a model with presets: pass `--voice preset --voice-name <name>`.
- `NotAuthenticated` or signing errors: check `OCI_AUTH` matches where you run, and test with
  `oci iam region list` (api_key) or `oci os ns get --auth resource_principal` (notebook).
- Warm-up reports `calibration failed`: the first requests errored; the error is printed above it.
- Timeouts at high concurrency are data: they are counted in `err` and the run continues.
- Every row in `requests.csv` carries the `opc-request-id`; quote it if you open an SR.
